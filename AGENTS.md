# Клон TINA: постоянные правила

- Единственный текущий список готовности — `docs/STATUS.md`; карта файлов — `README.md` и `docs/README.md`. После законченного изменения обновлять статус с конкретной проверкой и ограничениями. Датированные `reports/*.md` — история/доказательства, а не конкурирующие текущие планы. Временные файлы и резервные копии держать в `work/`, не в `src/`.

- Объём проекта — полный перенос TINA, включая лабораторные работы, а не только функции одной домашней работы. Очередность работ не уменьшает этот объём. Наличие пункта меню, расчёт через отдельный скрипт или результат оригинальной TINA не доказывают доступность функции через UI сайта. Готовность сценария подтверждать прохождением пользовательского пути на конкретной сборке; локальную и опубликованную версии проверять отдельно. Найденные ограничения явно фиксировать, не объявлять сайт готовым по частичному сценарию.

- Главная цель — настоящие **TSC для оригинальной TINA-TI 9.3.150**. Не добавлять JSON-проекты, свои контейнеры и лишние сохранения. Внутреннее восстановление браузера — не пользовательский формат.
- Сохранять работающую запись TSC. Все новые схемные данные действительно записывать в TSC; неизвестные записи сохранять побайтно, поля не выдумывать.
- Совместимые улучшения разрешены: если оригинальная TINA отображает результат через TSC, возможность можно оставить, даже если её нет в родном UI. Диагональные провода сохранять. Скругления/фотографии допустимы после подтверждения подходящей native записи, без отдельного формата. Не отключать весь редактор/диалог из-за отдельных неподдержанных подпунктов; серыми делать только их.
- Названия, порядок и расположение меню/инструментов/категорий соответствуют оригиналу, чтобы работать по методичке. Размеры/рисунок иконок могут отличаться. Неработающие команды серые, без «будет добавлено» и фиктивных действий.
- Новое пожелание пользователя: единый современный стиль всего сайта, скруглённые края и мягкий объём кнопок; не копировать старую Windows-оболочку. Названия/структура команд TINA сохраняются. Каталог большой и удобный, кнопки с пояснениями. Общие стили задавать одним набором токенов/правил, а не отдельно для каждого окна.
- Категории компонентов — настоящие вкладки общей панели («ящик»), соединённые с ней верхней гранью, а не подчёркнутая веб-навигация и не отдельные кнопки. Нейтральные серые поверхности без голубого отлива и градиентов. Объём сохранять границами и тенями.
- Эталон интерфейса: reports/reference-tina-editor-2026-10-25.png. Меню/каталог: src/native-menus.json и src/native-catalog.json.
- Работать семействами форматов и общими механизмами, подключая модели данными. Не исследовать каждый номинал/модель отдельно. Рабочий цикл: PORTING_WORKFLOW.md; индекс: reports/component-families.md.
- По умолчанию один основной агент. Делегирование — под конкретную независимую задачу; для простой задачи допустима Luna с коротким контекстом. Не распараллеливать всё автоматически.
- Сначала законченный пакет изменений, потом проверка. Для чистого интерфейса: сборка и визуальный просмотр, без новых тестов CSS/положения кнопок. Не гонять полный набор после каждой правки.
- Для TSC: пакетная проверка семейства и при необходимости представитель в оригинале. Полный набор — на завершённом функциональном этапе либо при конкретном риске регрессии. Повторять после изменений/ошибки.
- Читать точечно нужные файлы/разделы. Не печатать большие дампы, не перечитывать весь журнал и все инструменты. Кэшировать и переиспользовать исследования.
- Простые независимые задачи делегировать Luna с коротким контекстом. Не запускать дорогие модели для CSS, подписей и мелких исправлений; не дублировать работу агентов.
- Переносить поведение и окна по оригинальной TINA, а не конструировать аналоги по буквальному описанию пользователя. Сохранять состав, порядок и названия полей; неподдержанные поля серые. Не заменять нативные окна придуманными формами координат. Геометрию, цвета и положение подписей сверять с нативными данными/снимком; предположения не объявлять подтверждённым переносом.
- REA — под конкретный неизвестный факт об оригинале, когда существующих данных недостаточно. Не повторять диагностику и анализ защищённого exe перед обычной правкой UI. Сходство структуры не является доказанной семантикой.
- Завершение — рабочий результат в актуальной пользовательской сборке, а не только отчёт/другая папка. Сообщать URL/версию и выполненные проверки; полную совместимость не заявлять без основания.
- Источник: BrowserTransfer/project; HostedTina — Git-зеркало. Синхронизировать нужные исходники/сборку, сохраняя .git и src/library.json; не удалять пользовательские изменения.
- Не продолжать старую домашку. Не публиковать пользовательские схемы/шаблоны library.json и данные установленной TINA без разрешения.
- Не раскрывать ключи. Редактор/сборка без внешних модельных API. Отдельные платные вызовы OpenRouter требуют явного разрешения на соответствующее действие.

- Различать ряды по эталону: верхние кнопки инструментов стоят вплотную, gap=0 внутри групп; между вкладками категорий есть маленькие зазоры. Ячейки палитры также вплотную. Не переносить правило расстояний с одного ряда на другой.

- Эталон поверхности/теней пользователя: №31 Squishy Toggle Buttons, Justin Windle https://codepen.io/soulwire/pen/neJZgM (https://msiter.ru/articles/60-klassnykh-knopok-na-css-s-animaciey). Мягкие многослойные наружные и внутренние тени, светлый верхний блик и продавленное активное состояние; это эталон материала, а не требование сделать инструменты круглыми.

- Последнее уточнение 26.10: у кнопок нет теней в покое; при наведении лёгкое внутреннее вдавливание, при нажатии/активном инструменте более глубокое. Фон при этом не сереет; никаких наружных выпуклых теней. Общий отклик в src/button-feedback.css.

- Цветовой эталон — присланный снимок Google Docs: один общий светлый фон chrome, белые рабочие поверхности, единый цвет границ, основной и вторичный текст. Все цвета интерфейса брать из токенов theme.css, не назначать разные серые каждой панели/кнопке. Геометрию вкладок и плотность групп не менять при правках палитры.

- Формы компонентов: нативная узнаваемая форма, аккуратные SVG-линии; пиксельные неровности оригинала копировать не нужно. Миниатюры COMPREGE.BMP и WMF-геометрия 17 создаваемых семейств извлечены локально; инструкции NATIVE_ASSETS.md. Не возвращать произвольные квадраты/волны вместо соответствующих исходному типу обозначений. Все семейства используют общий рендерер src/native-symbol-vectors.ts. В Git-зеркало не копировать data/** и dist/tina/**.

- Учебные отчёты оформлять по предыдущим работам пользователя: настоящий титульник, портретный A4, Times New Roman 14 и структура методички. Не включать разработку сайта, перенос TSC, тестирование движков и технические сравнения в сдаваемую учебную работу; эти сведения хранить отдельно.
- Массовые варианты выполнять общим сценарным путём через UI сайта; оригинальная TINA затем автоматически открывает сохранённые TSC, запускает сохранённый анализ и снимает настоящие окна. Не повторять ручную сборку/настройку для каждого варианта.
- Перед учебной работой составить короткую карту требований исходной методички с номерами страниц, включая практический раздел и новые материалы занятия. Общая инструкция относится ко всем вариантам; модельные числа допускаются только в явно отмеченном примере.
- Таблица h-параметров не заменяет четыре графических определения с точками, координатами, разностями и подстановкой. Выходное семейство с гиперболой мощности показывать отдельно в физических осях; совмещённая диаграмма не заменяет этот рисунок. Для разных вариантов сохранять общие обязательные роли рисунков.
- Не объявлять отчёт готовым по наличию файлов, прохождению расчёта или числу страниц. Сверить содержимое с картой требований и визуально проверить читаемость всех построений. Выбор паспорта производителя должен быть единым для пределов тока, мощности и остальных паспортных данных.
