# Экономный перенос TINA

## Рабочий цикл

1. Один законченный пакет: вся компоновка интерфейса или одно семейство записей TSC.
2. Сначала существующий профиль/донор/отчёт. Уже полученные сведения не исследовать заново.
3. Для нового неизвестного поля — один минимальный before/after опыт или точный вопрос REA. Кандидат похожей структуры ещё не доказанный формат.
4. Общий механизм семейства + модели как данные. Не писать отдельный код и не запускать агента на каждый номинал или диод.
5. Проверка после пакета: UI — сборка и визуальный просмотр; TSC — пакетная проверка семейства и представитель в оригинале. Повторять только после изменений/ошибки.
6. Проверить именно актуальную пользовательскую сборку, сохранить короткую сводку и следующий неизвестный факт.

Архитектура переноса: общий конверт TSC → подтверждённый заголовок символа → профиль семейства (геометрия, выводы, параметры, версии) → каталог нативных моделей. UI команд хранится отдельно. Неизвестные записи сохраняются без изменений.

Пользователь разрешает улучшения интерфейса и новые возможности при сохранении отображения в оригинале через TSC. Диагонали сохраняются. Скругления и фотографии — допустимые будущие направления исследования, а не готовые функции. Отдельный недоступный подпункт не является поводом выключать весь диалог текста или другого редактора.

`tools/catalog-families.ts` инвентаризирует все локальные примеры одним проходом и сохраняет краткий индекс. Следующее исследование начинает с нужной строки, а не с повторного чтения всего каталога.

## Короткое задание агенту

> Перенеси [семейство/сценарий] из TINA. Результат — TSC, открываемый оригиналом. Используй [профиль и доноры], найди общую структуру и подключи представителей данными. Не меняй [границы]. Сначала выполни весь пакет, затем одну пакетную проверку. Для UI не пиши тесты компоновки. Не запускай других агентов и повторные исследования без конкретной необходимости. Покажи рабочую сборку и коротко перечисли неизвестное.

## Инструменты без магии

REA предоставляет агенту исследование архивов, ресурсов, строк, функций и связей, а также поддерживаемых runtime. Для глубокого native анализа используются движки вроде Ghidra/Hopper/IDA. REA не превращает exe в сайт и не гарантирует восстановление исходников. Для нашей TINA он нужен под конкретный неизвестный факт; копирование меню по снимку его не требует.

WebAssembly/Emscripten применимы к подходящему исходному C/C++ и переносимым зависимостям. Одного Windows exe недостаточно для пересборки в WebAssembly. Здесь редактор реконструируется отдельно, а совместимость обеспечивается настоящим TSC и оригинальной TINA.

## Прочитанные источники

- [OpenAI: пересмотр skills/prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra): сокращать накопившиеся инструкции и лишний контекст.
- [Anthropic: context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents): релевантный контекст, компактные заметки, получение данных по необходимости.
- [Anthropic: Building effective agents](https://www.anthropic.com/research/building-effective-agents): простые рабочие процессы, усложнение только при необходимости.
- [Kief Morris: Humans and Agents in Software Engineering Loops](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html): управлять циклом и оценивать работающий результат.
- [REA, официальный репозиторий](https://github.com/ACEpaincaster/rea-agents): движки анализа, возможности и ограничения восстановления кода.
- [Emscripten: Porting](https://emscripten.org/docs/porting/index.html): перенос C/C++ и отличия браузерной среды, файловой системы, графики и потоков.

Порядок работы выше — наше решение под требования пользователя, не обещание фиксированной экономии лимита аккаунта.
